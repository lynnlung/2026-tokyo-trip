# 系統架構

## 系統概覽

本網站採用無建置步驟的靜態前端，部署於 GitHub Pages；報名資料由 Google Apps Script 網頁應用程式接收並寫入 Google 試算表。

```text
瀏覽器
  ├─ index.html：頁面結構、旅遊行程、報名表單
  ├─ styles.css：桌面與手機版面
  └─ app.js：表單驗證、送出與結果顯示
          │ HTTPS POST（no-cors；表單編碼）
          ▼
Google Apps Script 網頁應用程式
  ├─ doPost：驗證必要欄位、建立/取得工作表、寫入報名
  └─ doGet：依 requestId 讀取短期結果快取，以 JSONP 回報
          │
          ▼
Google 試算表「2026公司旅遊」／工作表「報名資料」
```

## 元件與檔案

| 元件 | 位置 | 職責 |
|---|---|---|
| 網頁內容 | `index.html` | 導覽列、活動視覺、四日行程、報名表單與無障礙狀態訊息。 |
| 網頁樣式 | `styles.css` | 色彩、排版、欄位與按鈕樣式；在 680px 以下改為單欄版面，並另有 900px、1500px 的版面調整。 |
| 表單前端 | `app.js` | 必填欄位與 Email 格式驗證、送出表單、查詢結果及顯示狀態。Apps Script `/exec` 網址目前設定於此檔。 |
| 資料後端 | `apps-script/Code.gs` | 建立/取得 Google 試算表與工作表、保存報名及提供提交結果回呼。 |
| 本機預覽 | `preview-server.js` | 使用 Node.js 提供本機靜態 HTTP 預覽，監聽 `127.0.0.1:8000`。 |
| 活動圖片 | `東京旅遊春日拼貼海報.png` | 首頁活動主視覺。 |

## 報名資料流程

1. 使用者送出表單後，`app.js` 檢查姓名、手機、LINE 是否非空，並檢查非空 Email 是否符合瀏覽器 Email 格式。
2. 前端建立 UUID 作為 `requestId`，把表單欄位與此 ID 編碼後，以 `fetch` 的 `no-cors` POST 傳送至 Apps Script。因瀏覽器不允許讀取此 POST 的跨來源回應，POST 回應本身不作為成功依據。
3. `doPost` 再次檢查姓名、手機、LINE；建立或取得「2026公司旅遊」試算表及「報名資料」工作表，追加資料列。
4. Apps Script 將成功或失敗結果以 `requestId` 為鍵存入 Script Cache，快取有效期為 300 秒。手機欄先設定為純文字，再寫入含前導零的號碼。
5. POST 完成後，前端以載入 Apps Script 回傳的 JavaScript（JSONP）查詢同一個 `requestId`。`doGet` 回呼 `window.__receiveRegistrationStatus(...)`，前端依結果顯示成功或失敗。

## 試算表資料欄位

工作表第一列標題順序為：`姓名`、`Email`、`電話`、`LINE`、`報名時間`。Email 可留白；姓名、電話、LINE 為必填。報名時間由 Apps Script 以 `new Date()` 寫入。

## 跨來源與資料處理注意事項

- 網頁與 Apps Script 位於不同網域。現行流程刻意採用表單編碼的 `no-cors` POST 與 JSONP 結果查詢，不使用 iframe 或讀取 POST 的 CORS 回應。
- 報名個資只放在 POST body；JSONP 查詢參數僅有隨機 `requestId`。不要把姓名、Email、電話或 LINE 放入網址、查詢參數或前端日誌。
- Apps Script 網頁應用程式設定為以部署者身分執行並允許公開存取。此設定讓公開網站能寫入試算表，也代表必須妥善管理公開端點及試算表權限。
- Script Cache 只用於短暫回報結果，不是報名資料的儲存位置。資料以試算表為準。
- `no-cors` POST 不能讓瀏覽器判斷伺服器是否已收到請求。若寫入成功但結果查詢逾時，使用者可能看到失敗訊息；重送可能產生重複列，請先檢查試算表再協助重送。
- 前端與 Apps Script 各自檢查必填欄位；Email 格式目前由瀏覽器驗證，Apps Script 不重做 Email 格式驗證。
