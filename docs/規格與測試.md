# 規格與測試

## 需求規格

### 頁面與內容

- 活動名稱：2026 東京旅遊；視覺採春日、明亮活潑風格。
- 頁面由上而下包含導覽列、活動主視覺，以及「行程內容 | 報名表單」區塊。
- 主視覺使用 `東京旅遊春日拼貼海報.png`，以圓形圖片呈現。
- 四日行程依序為：第一天淺草寺、第二天河口湖、第三天晴空塔、第四天回家。
- 支援桌面與手機瀏覽；小螢幕時行程與表單改為上下排列。

### 報名表單

| 欄位 | 必填 | 規則 |
|---|---:|---|
| 姓名 | 是 | 不可為空白。 |
| Email | 否 | 留白可送出；有填寫時必須符合瀏覽器 Email 格式。 |
| 手機 | 是 | 不可為空白；儲存於試算表時必須保留文字型態與前導零。 |
| LINE | 是 | 不可為空白。 |

送出成功時顯示成功訊息並清空表單；失敗時顯示錯誤訊息。送出期間按鈕停用，避免使用者連續點擊。

### 資料儲存

- 試算表名稱：`2026公司旅遊`。
- 工作表名稱：`報名資料`。
- 標題列順序：姓名、Email、電話、LINE、報名時間。
- 電話欄以純文字儲存，避免手機前導零遺失。
- 詳細資料流與跨來源處理方式請參閱[系統架構](./系統架構.md)。

## 驗收測試清單

下列清單可供每次修改前端、Apps Script 或部署設定後重跑。

### 靜態檢查

- [ ] `node --check app.js` 通過。
- [ ] 確認 Apps Script 編輯器沒有語法錯誤，並檢查部署版本與程式碼一致。
- [ ] 本機預覽首頁、CSS 與海報皆可載入，瀏覽器 Console 無阻斷使用的錯誤。

### 頁面與表單

- [ ] 首頁順序為導覽列、活動主視覺、行程與報名表單；導覽連結能跳至對應區塊。
- [ ] 四日行程名稱與順序符合規格。
- [ ] 桌面與手機尺寸版面正常；表單在小螢幕易於閱讀與操作。
- [ ] 空白姓名、手機或 LINE 不能送出，且顯示錯誤提示。
- [ ] Email 留白可送出；格式錯誤的 Email 不能送出。
- [ ] 有效資料送出期間按鈕停用；收到成功結果後顯示成功訊息、清空欄位並重新啟用按鈕。
- [ ] 模擬後端失敗或結果逾時時，顯示失敗訊息而非成功訊息。

### Google 試算表端到端測試

1. 使用明確標記為測試的合成資料（不要使用真實個資），在公開網站或本機預覽各送出一筆。
2. 確認畫面收到成功訊息，並在「報名資料」工作表看到對應列及正確欄位。
3. 使用以 `0` 開頭的測試手機號碼，確認試算表顯示完整前導零，且電話欄格式為純文字。
4. 確認報名時間有寫入，Email 留白仍可成功。
5. 測試後依資料管理政策清除測試列；清除前先確認不是實際報名資料。
